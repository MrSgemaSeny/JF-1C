## 2. Анализ экосистемы проектов

### 2.1. JF-1C (ZhanFinance) — Ядро финансово-бухгалтерской SaaS CRM
- **Назначение**: SaaS-система автоматизации бухгалтерского аутсорсинга и операционного учета для малого и среднего бизнеса Республики Казахстан.
- **Архитектурный паттерн**: Модульный монолит со строгим разделением доменов (CRM, Billing, LMS, Documents, Chat, Notifications, Audit).
- **Стек**: Spring Boot 3, Java 17, PostgreSQL, React 19, TypeScript, Tailwind CSS v4, Feature-Sliced Design (FSD).
- **Инженерные особенности**:
  - Непрерывная цепочка из 121 миграции Flyway с гарантией обратной совместимости и защитой контрольных сумм.
  - Аудит изменений данных на уровне ядра СУБД (PostgreSQL triggers, append-only аудит-лог).
  - Разграничение доступа на уровне записей через выделенный CrmAccessService с проверкой прав владения сущностями (защита от IDOR).
  - Событийно-ориентированная архитектура фоновых задач (Spring Domain Events с аннотацией TransactionalEventListener phase AFTER_COMMIT) для предотвращения гонок транзакций при отправке email и уведомлений.
  - Полнофункциональное клиентское и сотрудницкое рабочее пространство с раздельными ролевыми интерфейсами.

### 2.2. Brain's Protocol (Second Brain) — Операционная система инженерного контекста
- **Назначение**: Исполняемая база архитектурных решений, контекста и аппаратных хуков для совместной разработки человека и автономных ИИ-агентов.
- **Архитектурный паттерн**: Расширенный Zettelkasten с жизненным циклом сессий и хуками на уровне файловой системы (`.agents`).
- **Стек**: Markdown, Obsidian, PowerShell/Bash scripts, Git.
- **Инженерные особенности**:
  - Более 60 структурированных концептуальных статей и свыше 15 формализованных Architectural Decision Records (ADR).
  - Непрерывный ежедневный журнал разработки (более 2400 коммитов в год).
  - Механизм внешних pre-commit / post-run хуков, управляющий пересчетом контрольных сумм, проверкой тестов и синхронизацией артефактов без ручного вмешательства.
  - Предотвращение деградации контекста больших языковых моделей за счет структурированного разделения оперативной и долговременной памяти.

### 2.3. MeDev (DevProfile) — Платформа профилирования и ИИ-анализа резюме
- **Назначение**: Сервис глубокого семантического анализа инженерных профилей и резюме с использованием открытых LLM.
- **Архитектурный паттерн**: Микросервис на FastAPI / Spring Boot с потоковой отдачей ответов.
- **Стек**: Spring Boot / Python, Server-Sent Events (SSE), Llama 3.3.
- **Инженерные особенности**:
  - Потоковая генерация и реактивная передача токенов через SSE без блокировки серверных потоков.
  - Устойчивый парсинг неструктурированных форматов резюме (PDF, DOCX, Markdown) с валидацией схем через JSON-Schema.
  - Изоляция пользовательских сессий анализа.

### 2.4. MrDevCourses (LMS с гибридным RAG)
- **Назначение**: Образовательная платформа с интеллектуальным поиском и поддержкой студентов через контекстный RAG.
- **Архитектурный паттерн**: Transactional Outbox + Eventual Consistency для межмодульных событий.
- **Стек**: Spring Boot, PostgreSQL с расширением pgvector, React, WebSocket.
- **Инженерные особенности**:
  - Гибридный поиск: комбинация векторного поиска по графам HNSW с полнотекстовым поиском PostgreSQL (Full-Text Search) через ранжирование Reciprocal Rank Fusion (RRF).
  - Локальный семантический чанкинг учебных материалов с сохранением контекстных границ лекций и кода.
  - Фильтрация входящих промптов (PromptSanitizer) для защиты от Prompt Injection.

### 2.5. Valeur — Мультитенантная SaaS-платформа
- **Назначение**: Распределенная B2B-система с изоляцией данных организаций.
- **Архитектурный паттерн**: Shared Database, Separate Schema / Discriminator Column с контролем через контекст потока.
- **Стек**: Spring Cloud Gateway, Spring Boot, PostgreSQL, Redis.
- **Инженерные особенности**:
  - Автоматическое связывание входящего JWT с TenantContext (ThreadLocal) на уровне фильтра шлюза.
  - Изоляция данных на уровне Hibernate-фильтров и динамических политик доступа.

## 4. Ключевые сильные стороны инженера

1. **Глубокая архитектурная дисциплина**:
   - Отказ от хаотичного добавления кода в пользу документирования архитектурных решений (ADR) и строгого ведения базы знаний.
   - Понимание физических ограничений баз данных: использование подходящих типов данных, составных индексов, оптимизация планов выполнения запросов, предотвращение N+1 проблем.

2. **Производственный уровень безопасности (Enterprise-grade Security)**:
   - Проверка прав владения на каждом уровне стека (от шлюза до репозитория).
   - Защита сессий, отсутствие уязвимостей массового присвоения (Mass Assignment) за счет разделения DTO и сущностей домена.

3. **Собственная методология работы с AI-агентами**:
   - Переход от роли простого оператора подсказок (prompt user) к архитектору автономных систем, где ИИ управляется детерминированными правилами, ограничениями и протоколами валидации.

## 5. Анализ архитектурных компромиссов и план устранения технического долга

В ходе аудита выявлены ключевые узлы системы, требующие плановой модернизации по мере роста пользовательской базы:

1. **Хранение бинарных документов в PostgreSQL (BYTEA)**:
   - *Текущее состояние*: Документы и печатные формы хранятся в бинарных полях БД с локальным фоллбэком.
   - *Риск*: При росте объема документов база данных быстро вырастет в гигабайтах, что замедлит создание резервных копий и увеличит нагрузку на буферный пул памяти СУБД.
   - *Решение*: Вынос хранения файлов в S3-совместимое объектное хранилище (Cloudflare R2 / MinIO / AWS S3) с сохранением в БД только метаданных, контрольных сумм SHA-256 и ключей доступа.

2. **Платформенная зависимость хуков автоматизации**:
   - *Текущее состояние*: Скрипты протокола автоматизации (`.agents`) написаны на PowerShell и оптимизированы для Windows-окружения.
   - *Риск*: Затруднен запуск в Linux-контейнерах и гетерогенных средах CI/CD без установки PowerShell Core.
   - *Решение*: Постепенная кроссплатформенная унификация служебных скриптов на Node.js/TypeScript или Bash/Python.

3. **Локальный лимитер запросов в оперативной памяти**:
   - *Текущее состояние*: Фильтры ограничения запросов используют локальный кэш (Caffeine / in-memory Bucket4j).
   - *Риск*: При горизонтальном масштабировании бэкенда на несколько реплик счетчики запросов станут изолированными для каждого узла.
   - *Решение*: Переход на распределенный Redis-бэкенд для Bucket4j при запуске более одного инстанса бэкенда.

4. **Защита внешнего периметра (WAF)**:
   - *Текущее состояние*: Защита обеспечивается фильтрами приложения на уровне Spring Security.
   - *Решение*: Подключение Cloudflare перед пользовательским доменом (zhanfinance.kz) для блокировки DDoS-атак и фильтрации трафика ботов до попадания на сервер приложений.

## 6. Стратегический план развития (Roadmap)

1. **Фаза 1: Интеграционный периметр (Q3-Q4 2026)**

3. **Фаза 3: Развитие Open-Source присутствия**
