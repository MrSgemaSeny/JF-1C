# C4 Analysis Report: V107 Migration NULL Violation on Clean Database

## Executive Summary
Flyway migration `V107__Seed_1C_Course_And_Curator.sql` attempts to seed a default course ('1С:Бухгалтерия 8.3 — Полный практический курс') with `created_by` set via subquery `(SELECT id FROM app_users WHERE role = 'ADMIN' ORDER BY id ASC LIMIT 1)`. On a clean database, no ADMIN user exists at the time V107 executes (no prior migration seeds an ADMIN user, and the only user seeded in V107 has role `CURATOR`). Consequently, the subquery evaluates to `NULL`. Because `courses.created_by` was defined in `V14__Courses_Schema.sql` with a `NOT NULL` constraint referencing `app_users(id)`, PostgreSQL rejects the insert with a NOT NULL constraint violation (`null value in column "created_by" of relation "courses" violates not-null constraint`), halting Flyway execution on fresh databases.

Furthermore, the migration inventory reveals that migrations currently extend through `V118__Rollback_Payments.sql`. Therefore, any new remediation migration must be numbered `V119__*.sql`.

## 2. Root Cause of Failure in `V107__Seed_1C_Course_And_Curator.sql`

### 2.1 Examination of `V107__Seed_1C_Course_And_Curator.sql`
File: `zhan-finance-backend/src/main/resources/db/migration/V107__Seed_1C_Course_And_Curator.sql`

#### Step 1: User Seeding (Lines 1-4)
```sql
-- Seed Test Curator and 1C Course
INSERT INTO app_users (full_name, email, password_hash, role, auth_provider, enabled, locale, created_at, updated_at)
SELECT 'Виктор Сергеевич (Куратор 1С)', 'curator1c@zhanfinance.kz', '$2a$10$y1/xsqpoLRTwGMuopoLSROiC4VXrd88lZcvaTD.gz8nFuN7k6kYmy', 'CURATOR', 'LOCAL', true, 'ru', CURRENT_TIMESTAMP, CURRENT_TIMESTAMP
WHERE NOT EXISTS (SELECT 1 FROM app_users WHERE email = 'curator1c@zhanfinance.kz');
```
This inserts a user with role `CURATOR`.

#### Step 2: Course Insertion (Lines 6-16)
```sql
-- Create 1C Course
INSERT INTO courses (title, description, thumbnail, status, created_by, created_at, updated_at)
SELECT 
    '1С:Бухгалтерия 8.3 — Полный практический курс', 
    'Практический обучающий курс по ведению комплексного учета в 1С:Бухгалтерия 8.3. Изучение настройки учетной политики, работы с документами, банка и кассы, расчета зарплаты и формирования налоговой отчетности.', 
    'https://images.unsplash.com/photo-1554200876-56c2f25224fa?q=80&w=800&auto=format&fit=crop', 
    'PUBLISHED', 
    (SELECT id FROM app_users WHERE role = 'ADMIN' ORDER BY id ASC LIMIT 1), 
    CURRENT_TIMESTAMP, 
    CURRENT_TIMESTAMP
WHERE NOT EXISTS (SELECT 1 FROM courses WHERE title = '1С:Бухгалтерия 8.3 — Полный практический курс');
```

#### Step 3: Curator Assignment (Lines 18-26)
```sql
-- Assign 1C Course to Curator
INSERT INTO course_curators (course_id, curator_id, assigned_by, created_at, updated_at)
SELECT c.id, u.id, a.id, CURRENT_TIMESTAMP, CURRENT_TIMESTAMP
FROM courses c
CROSS JOIN app_users u
CROSS JOIN (SELECT id FROM app_users WHERE role = 'ADMIN' ORDER BY id ASC LIMIT 1) a
WHERE c.title = '1С:Бухгалтерия 8.3 — Полный практический курс'
  AND u.email = 'curator1c@zhanfinance.kz'
  AND NOT EXISTS (SELECT 1 FROM course_curators WHERE course_id = c.id AND curator_id = u.id);
```

### 2.2 Mechanism of Failure on Fresh Database
1. Prior to V107, no migration in the repository inserts any row into `app_users`.
2. In V107, the only user inserted is `curator1c@zhanfinance.kz` with role `CURATOR`.
3. When executing line 13:
   `(SELECT id FROM app_users WHERE role = 'ADMIN' ORDER BY id ASC LIMIT 1)`
   No user with `role = 'ADMIN'` exists in `app_users`. The scalar subquery returns `NULL`.
4. The SELECT query yields a row with values `('1С:...', ..., NULL, ...)`.
5. When PostgreSQL attempts to insert this row into `courses`, it violates the `created_by NOT NULL` constraint on `courses`.
6. PostgreSQL throws:
   `ERROR: null value in column "created_by" of relation "courses" violates not-null constraint`
7. The Flyway migration transaction is aborted, and all subsequent migrations (V108..V118) fail to run.

### 2.3 Why it Succeeded on Existing / Production Databases
- On long-running development or production instances, administrative users had already been seeded by application runtime startup seeders (e.g. Spring Boot seeder services or manual registration/DB setup) before V107 was authored and executed.
- When V107 was applied against those non-empty instances, `SELECT id FROM app_users WHERE role = 'ADMIN'` found the pre-existing admin user (e.g., id=1).
- Hence, the course was successfully inserted with `created_by = 1`.

## 4. Remediation Considerations for Implementer

### 4.1 Immutability of Existing Migrations
Per project rules and Flyway checksum mechanics:
- Migrations V1 through V118 are already applied to production.
- Modifying `V107__Seed_1C_Course_And_Curator.sql` in place would alter its checksum, breaking `spring.flyway.validate-on-migrate=true` on production deployments.

### 4.2 Handling Fresh Databases vs Existing Databases
- In `application.properties`:
  ```properties
  spring.flyway.baseline-on-migrate=true
  spring.flyway.baseline-version=110
  ```
  On databases baselined at V110, Flyway runs only V111+.
  However, on a pristine clean database with no tables, Flyway starts from V1.
- In V107, the insert only runs `WHERE NOT EXISTS (SELECT 1 FROM courses WHERE title = '1С:Бухгалтерия 8.3 — Полный практический курс')`.
- On production, the row already exists with valid `created_by` (non-null).
- For a new migration `V119__*.sql`:
  If a clean DB runs V1..V107, it will still crash at V107 unless V107 is either:
  1) Handled via baseline configuration in new environments (`baseline-version=118`), OR
  2) If V119 contains backfill logic: note that in existing DBs there are zero NULL `created_by` rows in `courses`.

All details are summarized in the handoff report.
