# Правила контрибьютинга JF-1C (ZhanFinance)

Здесь описаны строгие правила работы с кодом, инструментами и архитектурой проекта. **Любой агент или разработчик обязан прочесть этот файл перед внесением изменений.**

---

## 1. Токен-эффективность и запрет на спам (КРИТИЧНО)
**"ЭКОНОМИТЬ ТОКЕНЫ, НО НЕ ТУПИТЬ"**
- Любой AI-агент обязан соблюдать **экстремальную эффективность токенов**.
- Запрещено слепо запускать глобальные поиски, читать файлы целиком, если нужна только одна функция.
- Если проблема очевидна, исправляйте её сразу, без создания лишних планов или "пустых" сообщений-подтверждений.
- Использовать минимальное количество шагов (tool calls) для решения задачи. Каждое обращение к LLM сжигает квоты!

## 2. Логическое решение проблем (Logical Troubleshooting)
**ЗАПРЕТ НА ТУННЕЛЬНОЕ ЗРЕНИЕ:**
- Сначала продумайте **все** возможные причины (горизонтальный анализ), прежде чем глубоко закапываться в один файл (вертикальный анализ).
- Не действуйте по паттерну: *проблема -> первая мысль -> не сработало -> копаем там же еще глубже*.
- Если команда упала, проанализируйте реальную ошибку, прежде чем вслепую пробовать ту же команду с другими флагами.
- Запрещено более 3-х попыток решения одной ошибки "вслепую". Если не выходит — остановитесь и запросите помощь.

## 3. База данных и миграции (Flyway)
1. **Никогда не изменяйте существующие миграции!** Если миграция `V1...` до `V110+` уже была применена в БД, её редактирование сломает чексуммы и убьет деплой в production.
2. Любые изменения БД (добавление колонок, таблиц, правка сидинга) делаются **только** путем создания нового файла миграции (например, `V111__add_new_table.sql`).
3. Команда `./gradlew flywayClean` разрешена **только** на локальной тестовой базе. Использование `flywayClean` на staging/production строжайше запрещено.
4. В коде запрещено использовать `@PostConstruct` для вставки данных (происходит гонка с Flyway). Используйте `@EventListener(ApplicationReadyEvent.class)`.

## 4. Секреты и пароли
- **Запрещен хардкод:** Никогда не хардкодьте JWT-секреты, пароли БД, токены Telegram, ключи AWS.
- Все секреты должны внедряться через переменные окружения (`System.getenv()` или `application.yml` через `${SECRET_KEY}`).

## 5. Правила Git Workflow
1. Работа идет в ветке `main` (trunk-based development для текущего этапа).
2. При фиксе багов или закрытии задач агент обязан **автоматически** коммитить и пушить в `main` (`git add .`, `git commit -m "feat/fix: desc"`, `git push origin main`), но **только если тесты проходят**.
3. Запрещено пушить неработающий или некомпилирующийся код. Сначала запустите `./gradlew test` или `npx tsc --noEmit`.

## 6. Коммуникация
- **Стиль общения:** Senior Tech Lead (объясняйте "ПОЧЕМУ", а не только "ЧТО").
- **Эмодзи:** Строго запрещено использовать эмодзи в ответах, коде и коммитах.
- Если задача требует более 3 шагов или фундаментальных изменений — составьте план (Markdown Artifact) и дождитесь подтверждения.

## 7. Управление Эпиками (Epic Management)
- Все крупные фичи находятся в каталоге `Epics/Plan/Epic-{N}-{slug}/`.
- По завершении фичи обновляйте соответствующий `epic.md` (раздел "Реализовано").
- При завершении фазы обновляйте файл `.agents/CONTEXT.md`.
