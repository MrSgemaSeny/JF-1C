Документ охватывает все аспекты проекта: от архитектуры и технологического стека до правил разработки, модулей системы и регламентов эксплуатации.

## 1. Введение и обзор проекта

### 1.1 Что такое ZhanFinance

ZhanFinance (JF-1C) — это высокопроизводительная B2B SaaS-платформа, разработанная как полноценная альтернатива универсальным коробочным решениям типа Bitrix24 или amoCRM. Платформа специально адаптирована для казахстанского рынка и покрывает все ключевые потребности бухгалтерских компаний и финансовых консультантов.

Проект создан одним разработчиком (от junior до middle level) с фокусом на прагматичные решения: работающее важнее идеального, но безопасность и корректность не подлежат компромиссу. Платформа прошла путь от простой CRM до полноценной enterprise-системы с 14 модулями, 231 Java-классом, 36 сущностями базы данных, 63 страницами фронтенда и 179 компонентами React.

### 1.2 Основные возможности платформы

Платформа объединяет в себе несколько ключевых направлений автоматизации. CRM-система с Kanban-доской позволяет управлять воронкой продаж, распределять задачи между сотрудниками и отслеживать прогресс по каждому клиенту. Подсистема документооборота обеспечивает генерацию официальных документов (акты выполненных работ, счета-фактуры, договоры) в форматах PDF и DOCX с полной поддержкой кириллицы. Биллинг-модуль автоматизирует выставление счетов, управление подписками и отслеживание оплат. Образовательная платформа (LMS) предоставляет возможность создавать курсы с главами и уроками, отслеживать прогресс обучения и выдавать сертификаты. Коммуникационный модуль на базе WebSocket обеспечивает мгновенный обмен сообщениями между сотрудниками и клиентами. Публичные лендинговые страницы позволяют привлекать новых клиентов через веб-сайт с формами обратной связи.

### 1.3 Целевая аудитория

Платформа ориентирована на бухгалтерские компании малого и среднего бизнеса в Казахстане, финансовых консультантов, аудиторские фирмы и компании, оказывающие услуги по ведению бухгалтерии. Типичный пользователь системы — это бухгалтер, работающий с несколькими клиентами одновременно, которому требуется инструмент для отслеживания дедлайнов, обмена документами и координации с командой.

### 1.4 Production-ссылки

Бэкенд API доступен по адресу https://zhanfinance.fly.dev/api. Swagger UI доступен только в dev/staging окружениях — в production отключен (`springdoc.swagger-ui.enabled=false`) из соображений безопасности. Фронтенд SPA развернут на GitHub Pages по адресу https://mrsgemaseny.github.io/JF-1C. В будущем планируется переход на кастомный домен zhanfinance.kz с подключением Cloudflare для CDN и защиты.

## 2. Технологический стек

### 2.1 Бэкенд

Серверная часть платформы построена на современном Java-стеке с акцентом на стабильность и производительность. Ядро системы работает на Java 17 — версии с долгосрочной поддержкой, обеспечивающей баланс между новыми языковыми возможностями и совместимостью с библиотеками. Spring Boot 4.1.0 (pre-release/snapshot на момент 2026) и Spring Framework предоставляют инфраструктуру для построения RESTful API, управления транзакциями и внедрения зависимостей. ORM-слой реализован через Hibernate в связке с Spring Data JPA, что упрощает работу с базой данных через репозитории.

Для управления схемой базы данных используется Flyway версии 10+ с модулями flyway-core и flyway-database-postgresql. Миграции представляют собой SQL-скрипты с версионированием, что позволяет безопасно вносить изменения в структуру БД и откатывать их при необходимости. Текущая цепочка миграций включает версии от V1 до V110 и выше.

Сборка проекта осуществляется через Gradle — гибкий инструмент, поддерживающий как Java, так и другие JVM-языки. Для кэширования данных на уровне приложения используется Caffeine с per-region кэшированием, что обеспечивает низкую латентность для часто запрашиваемых данных без нагрузки на базу данных.

### 2.2 Безопасность аутентификации

Аутентификация реализована на основе JWT-токенов с полной поддержкой ротации и аннулирования сессий. Access-токен имеет короткий срок жизни и передаётся в заголовке Authorization, а refresh-токен хранится в httpOnly cookie для защиты от XSS-атак. Дополнительный уровень безопасности обеспечивается двухфакторной аутентификацией (2FA) на основе TOTP с генерацией QR-кодов и поддержкой резервных кодов восстановления.

Rate limiting реализован через Bucket4j и применяется на уровне фильтров Spring Security. Фильтры ApiRateLimitFilter и AuthRateLimitFilter ограничивают частоту запросов с одного IP-адреса, предотвращая брутфорс-атаки и злоупотребление API.

### 2.3 База данных

В качестве СУБД используется PostgreSQL 17.6 — мощная реляционная база данных с поддержкой сложных запросов, триггеров и процедур. На production-среде работает managed PostgreSQL от Fly.io, а для локальной разработки предусмотрен запуск через Docker Compose.

В PostgreSQL настроены триггеры, запрещающие выполнение UPDATE и DELETE операций на таблицах аудита, что гарантирует целостность журналирования действий пользователей. Это критически важно для соответствия требованиям финансового регулирования и внутреннего контроля.

### 2.4 Фронтенд

Клиентская часть представляет собой Single Page Application на React 19 с полной типизацией через TypeScript. Сборка осуществляется через Vite — быстрый инструмент с поддержкой Hot Module Replacement и оптимизацией бандла. Стилизация построена на Tailwind CSS v4 в связке с Vanilla CSS Design System для компонентов, требующих тонкой настройки, а анимации реализованы через Framer Motion.

Архитектура фронтенда следует методологии Feature-Sliced Design (FSD), которая разделяет код на слои: shared (общие утилиты), entities (бизнес-сущности), features (пользовательские сценарии), widgets (самостоятельные блоки UI) и pages (страницы приложения). Это обеспечивает модульность, переиспользуемость и упрощает навигацию в большой кодовой базе.

### 2.5 Состояние и запросы

Управление серверным состоянием осуществляется через TanStack React Query v5, который предоставляет кэширование запросов, автоматические ретраи при ошибках, пагинацию и инвалидацию кэша. Все сетевые запросы проходят через единую обёртку apiRequest в shared/api/http, что обеспечивает централизованную обработку ошибок, добавление заголовков авторизации и перехват ответов.

Локализация реализована через react-i18next с поддержкой русского и английского языков из коробки. Интерактивные элементы UI используют @dnd-kit для Kanban-драг-дропа, SunEditor для rich-text редактирования и Lucide Icons для иконографии.

### 2.6 Инфраструктура и деплой

Бэкенд развёрнут на платформе Fly.io в регионе Amsterdam в виде Docker-контейнера. Fly.io автоматически управляет репликацией, перезапуском упавших инстансов и распределением нагрузки. Фронтенд хостится на GitHub Pages — бесплатном CDN для статических сайтов, что обеспечивает глобальную доступность и низкую латентность.

CI/CD пайплайны реализованы через GitHub Actions и включают автоматическое тестирование, проверку типов TypeScript, сборку артефактов и деплой на целевые платформы. Ночные джобы выполняют резервное копирование базы данных и отправляют уведомления в Telegram-канал о статусе системы.

### 2.7 Мониторинг и обсервабилити

Для отслеживания здоровья системы используются несколько инструментов. Actuator health endpoints предоставляют информацию о состоянии приложения, подключении к БД и других компонентах. Prometheus-метрики собирают данные о производительности, количестве запросов и использовании ресурсов. UptimeRobot мониторит доступность endpoints и отправляет алерты при обнаружении проблем.

### 2.8 Коммуникации в реальном времени

Чат и уведомления работают поверх WebSocket через протокол STOMP с SockJS в качестве fallback-механизма. Авторизация подключений реализована на уровне топиков: пользователи могут подписываться только на каналы `/topic/chat/{userId}`, где userId соответствует их учетной записи. Это предотвращает подслушивание сообщений между пользователями.

### 2.9 Генерация документов

PDF-документы генерируются через связку Thymeleaf (шаблонизатор) и OpenHTMLtoPDF (рендерер), что обеспечивает полную поддержку кириллицы, сложной типографики и корпоративного брендинга. DOCX-документы создаются через poi-tl — библиотеку для программной работы с форматами Microsoft Office. DocumentGeneratorService предоставляет унифицированный интерфейс для генерации различных типов документов из шаблонов.

### 2.10 Тестирование

Бэкенд покрыт 74 unit-тестами на JUnit 5 и Mockito, обеспечивающими проверку критических сервисов и контроллеров. Тесты запускаются автоматически в CI/CD пайплайне и блокируют деплой при падении. Фронтенд использует Vitest для unit-тестирования компонентов и хуков.

## 3. Архитектура системы

### 3.1 Общая архитектура

Система построена по классической трехслойной архитектуре с разделением на presentation layer (фронтенд), application layer (бэкенд API) и data layer (PostgreSQL). Фронтенд представляет собой stateless SPA, которое взаимодействует с бэкендом исключительно через REST API и WebSocket. Бэкенд не хранит состояние сессий на сервере — вся информация о пользователе инкапсулирована в JWT-токене.

Клиент отправляет запросы на API, где они проходят через цепочку фильтров Spring Security (аутентификация, авторизация, rate limiting), затем попадают в контроллер соответствующего модуля, обрабатываются сервисом с возможным обращением к базе данных через репозитории, и ответ возвращается клиенту в формате JSON.

### 3.2 Архитектура бэкенда

Бэкенд организован модульно внутри пакета `com.example.zhanfinancebackend.modules`. Каждый модуль содержит типичную для Spring MVC структуру: controller (REST-эндпоинты), service (бизнес-логика), repository (доступ к данным), entity (JPA-сущности), dto (объекты передачи данных) и mapper (преобразователи между entity и dto).

Все API запросы проходят через контекстный путь `/api` и версионированы как `/v1/**`, что даёт итоговые пути `/api/v1/...`. Версионирование позволяет развивать API без ломания существующих интеграций — клиенты могут продолжать использовать старую версию, пока мигрируют на новую.

Общие компоненты вынесены в пакеты `common/` и `config/`:
- common/audit — Hibernate-слушатели для автоматического журналирования изменений
- common/config — базовые конфигурации приложения
- common/exception — централизованная обработка исключений
- common/filter — HTTP-фильтры (CORS, авторизация)
- common/response — стандартизированные ответы API

### 3.3 Архитектура фронтенда

Фронтенд следует методологии Feature-Sliced Design, которая решает проблему организации кода в больших приложениях. Структура слоёв:

- **app/** — инициализация приложения, провайдеры контекста (AuthContext, QueryClientProvider), роутер
- **pages/** — страницы приложения, соответствующие маршрутам (LoginPage, DashboardPage, AdminEmployeesPage, TasksPage)
- **widgets/** — крупные самостоятельные блоки UI (TaskKanbanBoard, DocumentViewer, ChatWidget)
- **features/** — пользовательские сценарии, инкапсулирующие логику фичи (contact-form, auth, 2fa-setup)
- **entities/** — бизнес-сущности с их моделями, API-клиентами и хуками (task, client, user, course)
- **shared/** — переиспользуемый код: api/http (обёртка запросов), ui (базовые компоненты), lib (утилиты), i18n (локализация)

### 3.4 Паттерны проектирования

В проекте применяются проверенные паттерны проектирования. Паттерн Repository используется для абстракции доступа к данным — каждый репозиторий наследует JpaRepository и может содержать кастомные запросы через @Query. Паттерн Service Layer инкапсулирует бизнес-логику, отделяя её от контроллеров и обеспечивая транзакционность. Паттерн DTO (Data Transfer Object) используется для передачи данных между слоями, что позволяет контролировать видимость полей и версионировать API. Паттерн Mapper преобразует объекты между слоями (Entity -> DTO, DTO -> Entity), используя MapStruct или ручные мапперы.

### 3.5 Поток данных аутентификации

Процесс аутентификации начинается с отправки учётных данных на эндпоинт `/api/v1/auth/login`. AuthService проверяет credentials, при необходимости запрашивает верификацию 2FA, и возвращает access-токен (в теле ответа) и refresh-токен (в httpOnly cookie). Access-токен содержит информацию о пользователе (id, email, роли) и имеет короткий срок жизни (1 час). Refresh-токен используется для получения нового access-токена без повторного ввода пароля и имеет срок жизни 7 дней.

При каждом запросе JwtAuthenticationFilter перехватывает Bearer-токен из заголовка Authorization, валидирует его через JwtService, извлекает информацию о пользователе и устанавливает SecurityContext для авторизации.

### 3.6 Кэширование

Caffeine cache используется для кэширования данных на уровне приложения с per-region политикой. Регион — это логическая группа кэшируемых данных, например, "pipelines" для пайплайнов CRM или "documents" для шаблонов документов. CacheConfig определяет настройки каждого региона: максимальный размер, время жизни записей, политику вытеснения.

Преимущества Caffeine перед Ehcache или Redis: интеграция с Spring, низкий overhead, синхронный доступ без сериализации, простота конфигурации. Недостаток — отсутствие распределённого кэша, что приемлемо для текущего масштаба приложения (single-instance deployment).

## 4. Модули бэкенда

### 4.1 Модуль Auth (Аутентификация и авторизация)

Модуль auth — фундамент всей системы, обеспечивающий идентификацию и аутентификацию пользователей. Он включает управление пользователями, генерацию и валидацию JWT-токенов, OAuth2 авторизацию через Google, двухфакторную аутентификацию (TOTP), rate limiting для защиты от брутфорса и регистрацию новых пользователей с модерацией.

Сущность User хранит информацию о пользователе: email, password (bcrypt-хеш), имя, фамилию, роль, статус регистрации (PENDING, APPROVED, REJECTED), флаги 2FA и метаданные. RefreshToken связывает пользователя с токеном обновления, его сроком жизни и device-информацией для security-аналитики. TwoFactorPreAuth хранит промежуточные токены при логине с включённой 2FA до успешной верификации.

Контроллеры модуля: AuthController обрабатывает логин, логаут, регистрацию, refresh-токены и Google OAuth; TwoFactorController управляет настройкой, верификацией и отключением 2FA; UserController предоставляет CRUD для профиля пользователя.

Сервисы модуля: AuthService инкапсулирует логику аутентификации; JwtService генерирует и валидирует токены; RefreshTokenService управляет жизненным циклом refresh-токенов; TwoFactorService реализует TOTP-функциональность; GoogleAuthService обрабатывает OAuth2 flow; UserService управляет пользователями.

### 4.2 Модуль CRM (Управление отношениями с клиентами)

CRM-модуль — ядро платформы, обеспечивающее управление задачами, клиентами, воронкой продаж и Kanban-доской. Это наиболее объёмный модуль системы, включающий множество связанных сущностей и сложную бизнес-логику.

Сущности модуля:
- **Task** — задача с заголовком, описанием, статусом, приоритетом, дедлайном, исполнителем и клиентом
- **Stage** — стадия воронки с типом (OPEN, CLOSED, LOST) и порядком отображения
- **Pipeline** — воронка продаж, содержащая набор стадий
- **Client** (ClientProfile) — профиль клиента с контактной информацией
- **Subtask** — подзадача, привязанная к родительской Task
- **TaskComment** — комментарий к задаче
- **TaskActivity** — история изменений задачи (журнал аудита на уровне задачи)
- **UserLabel** — пользовательская метка для категоризации задач
- **CalendarEvent** — событие календаря с датой и участниками
- **LeadSource** — источник лида (referral, website, cold call)

Сервисы модуля: TaskService управляет CRUD задач, подзадач, комментариями, назначением исполнителей; ClientService обрабатывает профили клиентов; PipelineService управляет воронками и стадиями; DashboardService предоставляет данные для дашбордов (статистика по задачам, загрузке сотрудников); CrmAccessService реализует проверку прав доступа на уровне записей (row-level security); PipelineSeederService инициализирует стартовые пайплайны при первом запуске.

### 4.3 Модуль Billing (Биллинг и финансы)

Модуль billing автоматизирует финансовые операции: выставление счетов, управление подписками, отслеживание оплат и генерацию финансовых документов.

Сущности модуля: Invoice представляет счёт на оплату с номером, датой, суммой, списком услуг, статусом (DRAFT, SENT, PAID, OVERDUE, CANCELLED) и ссылкой на клиента; Subscription описывает рекуррентную подписку с периодом (monthly, quarterly, yearly), ценой и датой следующего платежа.

Сервисы модуля: InvoiceService управляет жизненным циклом счетов; SubscriptionService обрабатывает подписки и автоматическое продление; PdfGeneratorService генерирует PDF-версии счетов; InvoiceOverdueScheduler проверяет просроченные счета и обновляет их статус; InvoiceAccessService обеспечивает row-level доступ к финансовым данным.

### 4.4 Модуль Documents (Документооборот)

Модуль documents обеспечивает хранение, генерацию и управление документами. Платформа поддерживает два хранилища: DatabaseStorageService сохраняет файлы в базе данных (метаданные + blob), а LocalStorageService — в файловой системе приложения как fallback.

Сущности модуля: DocumentTemplate хранит шаблоны документов с типом (PDF, DOCX), содержимым (Thymeleaf-шаблон или poi-tl шаблон) и переменными для подстановки; Document представляет сгенерированный или загруженный документ со ссылкой на шаблон, параметрами генерации и статусом; StoredFile хранит бинарные данные файлов с MIME-типом, именем и размером.

Сервисы модуля: DocumentService управляет документами; DocumentGeneratorService генерирует документы из шаблонов; DocumentTemplateService управляет шаблонами; StorageService определяет интерфейс хранилища; DocumentAccessService проверяет права доступа к документам; DocumentDataLoader загружает данные из БД для подстановки в шаблоны; OfficialDocumentTemplateSeeder инициализирует стандартные шаблоны.

Контроллеры модуля: DocumentController предоставляет CRUD для документов; DocumentTemplateController управляет шаблонами; FileDownloadController обеспечивает безопасное скачивание файлов с проверкой доступа.

### 4.5 Модуль Courses (LMS — Система управления обучением)

Модуль courses реализует полноценную систему управления обучением с поддержкой курсов, глав, уроков, прогресса и сертификации.

Сервисы модуля: NotificationService управляет уведомлениями; EmailNotificationService отправляет email через SMTP; TelegramNotifierService отправляет алерты в Telegram; DeadlineAlertScheduler проверяет дедлайны задач и отправляет напоминания.

### 4.8 Модуль Audit (Аудит)

Модуль audit обеспечивает журналирование всех действий пользователей в системе. HibernateAuditListener автоматически перехватывает операции INSERT, UPDATE, DELETE и записывает их в таблицу audit_log.

## 5. Структура фронтенда

### 5.1 Слои FSD

**Shared Layer** содержит код, переиспользуемый во всех частях приложения. В shared/api/ находится http.ts — централизованная обёртка над fetch для всех API-запросов. Она автоматически добавляет заголовки авторизации, обрабатывает refresh-токены, парсит JSON-ответы и транслирует ошибки. Shared/ui/ содержит базовые компоненты: кнопки, инпуты, модалки, карточки. Shared/lib/ включает утилиты: форматирование дат, валидация, хелперы. Shared/i18n/ настраивает react-i18next и хранит переводы.

**Entities Layer** определяет типы данных и операции для бизнес-сущностей. Каждая сущность имеет директорию с файлами:
- model.ts — TypeScript-интерфейс или тип
- api.ts — функции для API-запросов (используют apiRequest из shared)
- hooks/ — хуки для управления данными через React Query (useTask, useClient, useUser)

Сущности фронтенда включают: user (аутентификация, профиль), task (задачи, подзадачи), client (клиенты), pipeline (воронки), course (курсы), document (документы), invoice (счета), chat (сообщения), notification (уведомления), audit (журнал аудита), calendar (события).

**Features Layer** инкапсулирует пользовательские сценарии, объединяя несколько сущностей и UI. Примеры фичей:
- features/auth — логин, логаут, регистрация, восстановление пароля
- features/task — создание задачи, редактирование, комментарии
- features/2fa — настройка двухфакторной аутентификации
- features/contact-form — форма обратной связи
- features/leads — управление лидами
- features/task — операции с задачами
- features/notifications — управление уведомлениями
- features/labels — метки задач
- features/service-modal — модалка услуги

**Widgets Layer** содержит крупные, относительно независимые блоки UI, которые могут использоваться несколькими страницами. Примеры виджетов:
- widgets/task-board — Kanban-доска с драг-дропом
- widgets/chat/ — чат-виджет с WebSocket
- widgets/header/ — шапка приложения с навигацией
- widgets/footer/ — подвал
- widgets/dashboard/ — виджеты дашборда
- widgets/search/ — глобальный поиск
- widgets/task-create/ — форма создания задачи
- widgets/task-reject/ — диалог отклонения задачи

- widgets/reviews/ — отзывы
- widgets/hero/, widgets/trust/, widgets/team/, widgets/offices/ — секции лендинга

**Pages Layer** представляет собой страницы приложения, соответствующие маршрутам роутера. Каждая страница компонует виджеты и фичи для реализации пользовательского сценария. Страницы включают:
- pages/auth/ — LoginPage, RegisterPage
- pages/dashboard/ — DashboardPage
- pages/admin/ — AdminEmployeesPage, AdminClientsPage, AdminPipelinesPage, AdminDashboardPage

- pages/about/ — AboutPage

- Публичные страницы: Home, Services, About, Solution Picker, Contact, Leads

### 5.2 Управление состоянием

React Query управляет серверным состоянием — данными, которые приходят с API. Каждый хук использует структурированные query keys для организации кэша: ['tasks', 'list', filter] для списка задач, ['tasks', 'detail', id] для конкретной задачи. Это обеспечивает точную инвалидацию — изменение задачи инвалидирует только её кэш, не трогая остальные.

Локальное состояние (UI state) управляется через React hooks: useState для простых состояний, useReducer для сложных, useContext для состояния, доступного дереву компонентов (AuthContext для информации о пользователе).

### 5.3 Роутинг

Маршрутизация построена на react-router-dom с защитой маршрутов через компоненты-обёртки. Приватные маршруты (Dashboard, Admin) требуют аутентификации и проверяют роль пользователя. Публичные маршруты (Landing pages) доступны без авторизации.

### 5.4 Обработка ошибок

Централизованная обработка ошибок реализована на нескольких уровнях. HTTP-слой (shared/api/http) перехватывает HTTP-ошибки (401, 403, 404, 500) и транслирует их в typed exceptions. React Query настраивает retry-логику: 3 попытки с экспоненциальной задержкой для сетевых ошибок, немедленный fail для 4xx ошибок. UI-слой отображает ошибки через Toast-уведомления или inline-сообщения в зависимости от контекста.

### 5.5 WebSocket интеграция

STOMP-клиент подключается при инициализации приложения и использует JWT для аутентификации. Подписки на топики устанавливаются в компонентах, которым нужен real-time функционал (ChatWidget, NotificationsBell). При размонтировании компонента подписки отменяются для предотвращения утечек памяти.

## 6. База данных и миграции

### 6.1 Структура миграций

Flyway миграции располагаются в `zhan-finance-backend/src/main/resources/db/migration/` и именуются по шаблону `V{NN}__{description}.sql`, где NN — порядковый номер миграции, description — краткое описание на английском языке. Двойное подчёркивание между номером и описанием — требование Flyway.

Текущая цепочка миграций простирается от V1 до V110+. Каждая миграция добавляет новую функциональность: таблицы, колонки, индексы, данные. Старые миграции никогда не модифицируются после применения — это критическое правило.

### 6.2 Неизменяемость миграций

Flyway хранит checksum каждой применённой миграции в таблице flyway_schema_history. Изменение файла миграции приводит к несовпадению checksum и ошибке при запуске приложения. Это защитный механизм — он предотвращает случайное изменение схемы production-базы.

Если требуется изменить существующую структуру, создаётся новая миграция. Например, если нужно добавить колонку email_phone в таблицу clients, создаётся файл V111__add_phone_to_clients.sql с соответствующим ALTER TABLE.

### 6.3 Правила именования

Рекомендуемые префиксы для миграций:
- V{NN}__create_{table}.sql — создание таблицы
- V{NN}__add_{column}_to_{table}.sql — добавление колонки
- V{NN}__create_{index}_index.sql — создание индекса
- V{NN}__insert_{data}.sql — вставка начальных данных (сидинг)

### 6.4 Сидинг данных

Первичные данные (сидеры) создаются не через миграции, а через Spring-компоненты с аннотацией @EventListener(ApplicationReadyEvent.class). Это обеспечивает корректный порядок выполнения: миграции сначала, затем сидинг.

Пример: PipelineSeederService создаёт стандартные воронки после запуска приложения. @PostConstruct для сидинга использовать запрещено — это вызывает race condition с Flyway.

### 6.5 Локальная разработка

При локальной разработке используется baseline для существующей схемы. В application-dev.yml настроено `spring.flyway.baseline-version=110`, что позволяет применять новые миграции (V111+) к существующей БД без ошибок baseline.

### 6.6 Основные таблицы

Таблица app_users хранит пользователей системы. Таблица refresh_tokens связывает пользователей с refresh-токенами. Таблица tasks, stages, pipelines управляют CRM-функциональностью. Таблицы invoices, subscriptions обрабатывают биллинг. Таблицы courses, chapters, lessons, enrollments реализуют LMS. Таблицы documents, document_templates, stored_files обеспечивают документооборот. Таблица chat_messages хранит сообщения. Таблица notifications управляет уведомлениями. Таблица audit_log журналирует действия.

### 6.7 Индексы и оптимизация

Критические запросы оптимизированы через индексы:
- idx_tasks_assigned_user_id — поиск задач по исполнителю
- idx_tasks_client_id — задачи клиента
- idx_tasks_stage_id — задачи по стадии
- idx_refresh_tokens_user_id — поиск токенов пользователя
- idx_two_factor_pre_auth_expires_at — очистка просроченных записей

### 6.8 Триггеры защиты аудита

PostgreSQL триггеры на таблицах audit_log запрещают UPDATE и DELETE:
```sql
CREATE OR REPLACE FUNCTION prevent_audit_modification()
RETURNS TRIGGER AS $$
BEGIN
  RAISE EXCEPTION 'UPDATE and DELETE on audit tables are prohibited';
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER audit_log_no_update
  BEFORE UPDATE ON audit_log
  FOR EACH ROW EXECUTE FUNCTION prevent_audit_modification();
```

## 7. Безопасность и авторизация

### 7.1 Многоуровневая защита

Безопасность платформы реализована на нескольких уровнях. Network layer защищён через HTTPS на всех окружениях и Firewall на уровне инфраструктуры. Transport layer использует TLS для шифрования трафика. Application layer включает аутентификацию, авторизацию, rate limiting и валидацию ввода. Data layer обеспечивает row-level security и защиту аудита.

### 7.2 JWT-аутентификация

Access-токен содержитclaims: sub (user_id), email, roles[], iat (issued at), exp (expiration). Токен подписывается секретным ключом через HMAC-SHA256 и передаётся в заголовке Authorization: Bearer <token>. JwtService валидирует подпись и срок жизни токена при каждом запросе.

Refresh-токен хранится в httpOnly cookie и отправляется автоматически браузером. Это защищает от XSS-атаки (токен недоступен JavaScript). SameSite=strict предотвращает отправку cookie в cross-site запросах.

### 7.3 Row-Level Security (CrmAccessService)

Spring Security @PreAuthorize проверяет только роли: hasRole('ADMIN'), hasRole('EMPLOYEE'). Но этого недостаточно — сотрудник EMPLOYEE не должен видеть задачи других сотрудников. CrmAccessService реализует дополнительную проверку на уровне записей.

Пример проверки в TaskService:
```java
public TaskDto updateTask(Long taskId, TaskUpdateRequest request, Long userId) {
  Task task = taskRepository.findById(taskId)
    .orElseThrow(() -> new NotFoundException("Task not found"));
  
  // Row-level check
  if (!crmAccessService.canAccessTask(userId, task)) {
    throw new AccessDeniedException("You don't have access to this task");
  }
  
  // Business logic
  // ...
}
```

### 7.4 IDOR-защита на batch-операциях

Массовые операции (назначение нескольких задач, изменение статуса нескольких задач) требуют проверки доступа к каждому элементу отдельно. TaskBatchOperationRequest содержит список ID, и сервис итерирует по ним, проверяя доступ к каждому.

### 7.5 Rate Limiting

Bucket4j реализует token bucket algorithm для ограничения частоты запросов. ApiRateLimitFilter применяется ко всем эндпоинтам: 100 запросов в минуту с одного IP. AuthRateLimitFilter строже для auth-эндпоинтов: 5 попыток логина в минуту, 3 попытки регистрации в минуту.

При превышении лимита возвращается HTTP 429 Too Many Requests с заголовком Retry-After.

### 7.6 Input Validation

Все входные данные валидируются через Jakarta Validation annotations (@NotBlank, @Email, @Size, @Pattern). Сервисы не доверяют входным данным и повторно валидируют их при необходимости.

### 7.7 Output Encoding

JSON-ответы не содержат raw HTML — фронтенд отвечает за экранирование при отображении. PDF и DOCX документы генерируются через шаблонизаторы, которые автоматически экранируют пользовательский ввод.

### 7.8 Защита чувствительных данных

HibernateAuditListener маскирует SENSITIVE_FIELDS при записи в audit_log. К таким полям относятся: password, totpSecret, refreshToken. Bcrypt используется для хеширования паролей с cost factor 12.

### 7.9 2FA (TOTP)

Двухфакторная аутентификация реализована на основе RFC 6238 (TOTP). При настройке 2FA генерируется секрет (base32), создаётся QR-код с otpauth:// URI для сканирования приложением-аутентификатором. При логине после ввода пароля запрашивается 6-значный код, который валидируется через Time-based One-Time Password Algorithm.

Резервные коды (8 кодов по 10 символов) позволяют войти при утере устройства. Коды одноразовые — после использования удаляются.

## 8. Ролевая модель

### 8.1 Роли системы

Система определяет 6 ролей с различными правами доступа:

**ADMIN** — администратор системы. Полный доступ ко всем модулям и функциям. Может управлять пользователями, пайплайнами, настраивать систему, просматривать все данные. Типичное использование: владелец бизнеса, технический администратор.

**EMPLOYEE** — сотрудник компании. Доступ к назначенным задачам, клиентам и чатам. Может брать задачи из Task Pool, создавать подзадачи и комментарии. Типичное использование: бухгалтер, консультант.

**ADVISOR** — расширенный сотрудник. Полный доступ ко всем задачам и клиентам компании (сквозной доступ). Может просматривать аналитику, переназначать задачи. Типичное использование: старший консультант, руководитель группы.

**CLIENT** — клиент компании. Строго ограниченный доступ: видит только свои задачи, документы и счета. Не видит внутренних комментариев и чужих данных. Типичное использование: представитель компании-клиента.

**LEARNER** — ученик LMS-платформы. Доступ к купленным курсам и урокам. Может проходить обучение и получать сертификаты. Типичное использование: студент, новый сотрудник на обучении.

**CURATOR** — куратор курсов. Доступ к проверке заданий учеников и отслеживанию прогресса. Типичное использование: преподаватель, ментор.

### 8.2 Регистрация и модерация

Новые сотрудники проходят регистрацию со статусом PENDING. Администратор проверяет заявку и утверждает (APPROVED) или отклоняет (REJECTED). Только APPROVED пользователи могут входить в систему. Это предотвращает создание фейковых аккаунтов.

### 8.3 Права доступа по модулям

| Модуль        | ADMIN | EMPLOYEE | ADVISOR | CLIENT | LEARNER | CURATOR |
|---------------|-------|----------|---------|--------|---------|---------|
| Auth          | CRUD  | Read     | Read    | Read   | Read    | Read    |
| CRM Tasks     | CRUD  | Assigned + Pool | Full | Own | —      | —       |
| CRM Clients   | CRUD  | Assigned | Full    | Own    | —      | —       |
| CRM Pipelines | CRUD  | Read     | Full    | —      | —      | —       |
| Billing       | CRUD  | Assigned | Full    | Own    | —      | —       |
| Documents     | CRUD  | Assigned | Full    | Own    | —      | —       |
| LMS Courses   | CRUD  | —        | Read    | —      | Enrolled | CRUD  |
| Chat          | Read  | Dialogs  | Dialogs | Dialogs | —     | Dialogs |
| Notifications | CRUD  | Own      | Own     | Own    | Own     | Own     |

### 8.4 ADVISOR — особая роль

Роль ADVISOR заслуживает отдельного внимания. В типичной CRM бухгалтерской компании старший консультант должен видеть все процессы по всем клиентам для экспертного контроля. CrmAccessService реализует "穿透访问" (сквозной доступ) для ADVISOR — проверка владения задачей отключается, и запрос пропускается, если пользователь имеет роль ADVISOR.

```java
public boolean canAccessTask(Long userId, Task task) {
  if (hasRole(userId, Role.ADMIN)) return true;
  if (hasRole(userId, Role.ADVISOR)) return true; // Сквозной доступ
  
  // Для остальных — проверка владения
  return task.getAssignedUserId().equals(userId) 
      || task.getCreatedByUserId().equals(userId);
}
```

## 9. API и эндпоинты

### 9.1 Структура API

Все эндпоинты располагаются за контекстным путём /api и версионируются как /v1. Итоговые пути: /api/v1/{resource}. Swagger UI доступен в dev/staging окружениях по пути /swagger-ui.html (отключен в production).

Стандартные HTTP-методы используются по назначению:
- GET — получение данных (список или один ресурс)
- POST — создание ресурса
- PUT/PATCH — обновление ресурса
- DELETE — удаление ресурса

### 9.2 Формат ответов

Успешный ответ возвращает JSON:
```json
{
  "success": true,
  "data": { ... },
  "timestamp": "2026-08-07T10:30:00Z"
}
```

Ошибка возвращает JSON:
```json
{
  "success": false,
  "error": {
    "code": "TASK_NOT_FOUND",
    "message": "Задача с ID 123 не найдена"
  },
  "timestamp": "2026-08-07T10:30:00Z",
  "requestId": "req-uuid-123"
}
```

requestId связывает ошибку с логами для отладки.

### 9.3 Коды ошибок

ApiException с ErrorCode определяет тип ошибки:
- UNAUTHORIZED (401) — не аутентифицирован
- FORBIDDEN (403) — нет прав доступа
- NOT_FOUND (404) — ресурс не найден
- VALIDATION_ERROR (400) — ошибка валидации
- CONFLICT (409) — конфликт (дубликат email)
- RATE_LIMITED (429) — превышен лимит запросов
- INTERNAL_ERROR (500) — внутренняя ошибка сервера

## 10. Развертывание и инфраструктура

### 10.1 Хостинг

Бэкенд развёрнут на Fly.io — платформе для запуска контейнерных приложений. Преимущества Fly.io: автоматическое масштабирование, edge-распределение, простое управление через flyctl CLI, встроенная поддержка PostgreSQL.

Фронтенд развёрнут на GitHub Pages — бесплатном хостинге для статических сайтов. Каждый push в main автоматически деплоит обновлённую версию. Для SPA настроен fallback на index.html для всех маршрутов.

### 10.2 Docker

Бэкенд упакован в Docker-контейнер через Dockerfile в корне проекта. Multi-stage build минимизирует размер образа:
1. Build stage — компиляция Java, установка зависимостей
2. Runtime stage — минимальный образ с JRE

```dockerfile
FROM eclipse-temurin:17-jdk-alpine AS build
WORKDIR /app
COPY . .
RUN ./gradlew bootJar

FROM eclipse-temurin:17-jre-alpine
WORKDIR /app
COPY --from=build /app/build/libs/*.jar app.jar
ENTRYPOINT ["java", "-jar", "app.jar"]
```

### 10.3 CI/CD пайплайны

GitHub Actions автоматизирует процессы сборки, тестирования и деплоя.

**Frontend Pipeline (.github/workflows/ci.yml)**
- Триггер: push в main
- Шаги: checkout, setup Node.js, npm install, npm run build, deploy to GitHub Pages
- Fail-fast: тесты блокируют деплой

**Backend Pipeline (.github/workflows/deploy-backend.yml)**
- Триггер: изменения в zhan-finance-backend/**
- Шаги: checkout, setup Java, ./gradlew test, build Docker image, push to Fly.io, deploy

**Database Backup Pipeline (.github/workflows/db-backup.yml)**
- Триггер: ежедневно ночью
- Шаги: pg_dump, upload to artifacts, send Telegram notification

Никогда не хардкодить секреты в исходном коде!

## 12. Правила разработки

### 12.1 Принципы

**Security first** — безопасность важнее функциональности и производительности. Любое решение взвешивается с учётом security implications.

**Working over perfect** — работающий MVP важнее идеальной архитектуры. Рефакторинг делается, когда появляется понимание, что именно нужно улучшать.

**No premature optimization** — оптимизация делается при наличии измеримой проблемы, а не на основе предположений.

**Token efficiency** (для AI-агентов) — минимальное количество tool calls для решения задачи. Не читать файлы целиком, если нужна одна функция.

### 12.2 Git Workflow

Используется trunk-based development с основной веткой main:
1. Все изменения ведутся в main (для текущего этапа развития)
2. При фиксе багов или завершении задач — коммит и push в main
3. CI/CD автоматически деплоит после прохождения тестов

Сообщения коммитов:
```
feat(US-02.1): добавить создание подзадач в задачах
fix(US-09.2): исправить валидацию TOTP-кода
migration(V111): добавить индекс для часто-запрашиваемых задач
docs: обновить RUNBOOK
```

### 12.3 Code Style

Java код следует стандартным convetions с акцентом на читаемость. Фронтенд использует ESLint и Prettier для автоматического форматирования. TypeScript strict mode включён.

Основные правила:
- Имена классов — PascalCase (TaskService)
- Имена методов — camelCase (createTask)
- Имена констант — UPPER_SNAKE_CASE (MAX_RETRY_COUNT)
- Имена файлов — kebab-case (task-service.ts)
- Геттеры/setters не используются без необходимости
- Preference к immutability

### 12.4 Code Review

При работе с AI-агентами code review выполняется агентом автоматически. Для человеческого review:
- Проверка security implications
- Проверка соответствия архитектуре
- Проверка обработки edge cases
- Проверка тестового покрытия

### 12.5 Запрещённые практики

- Изменение применённых Flyway миграций
- Использование @PostConstruct для DB-операций
- Хардкод секретов в исходном коде
- Использование @Entity для объектов, не являющихся таблицами
- Создание God-classes с тысячами строк
- Игнорирование Exception handling
- SQL-инъекции через конкатенацию строк
- XSS через вывод непроверенного HTML

### 12.6 Error Handling

Все исключения перехватываются централизованным ExceptionHandler. Типы ошибок:
- ApiException — бизнес-ошибки с кодом и сообщением
- NotFoundException — ресурс не найден (404)
- AccessDeniedException — недостаточно прав (403)
- ValidationException — ошибка валидации (400)
- Все прочие — UnexpectedException (500)

Raw stack trace никогда не возвращается клиенту в production.

## 14. Регламент эксплуатации

### 14.1 Деплой

Деплой выполняется автоматически через GitHub Actions при push в main. Фронтенд деплоится на GitHub Pages, бэкенд — на Fly.io. Rollback выполняется через переключение на предыдущий Docker image на Fly.io или передеплой предыдущего commit на GitHub Pages.

### 14.2 Мониторинг

UptimeRobot проверяет endpoints каждые 5 минут. При недоступности отправляется алерт в Telegram. Логи приложения доступны через `flyctl logs`.

### 14.3 Резервное копирование

Ночной бэкап базы данных выполняется в 03:00 по UTC. pg_dump архивируется в gzip и сохраняется в GitHub Actions artifacts. Retention: 30 дней.

### 14.4 Восстановление

```bash
# Скачать бэкап из artifacts или хранилища
gunzip -c backup_2026-08-01.sql.gz | psql -h <host> -U postgres -d zhan_finance_db
```

### 14.5 Incident Response

**Сценарий A: CORS ошибки на WebSocket**
- Симптом: CORS policy и 404 на /ws/info
- Причина: Фронтенд обращается мимо контекста /api
- Действие: Проверить getWsEndpointUrl в http.ts — должен быть /api/ws

**Сценарий B: ChunkLoadError после деплоя**
- Симптом: 404 на JS-чанках при навигации
- Причина: Браузер закэшировал старый index.html
- Действие: Ctrl+F5 для очистки кэша

**Сценарий C: 429 Too Many Requests**
- Симптом: HTTP 429 от API
- Причина: Сработал rate limiter
- Действие: Подождать минуту или проверить частоту запросов

**Сценарий D: Flyway Checksum Error**
- Симптом: Приложение не стартует, checksum mismatch
- Причина: Изменение применённой миграции
- Действие: Создать компенсирующую миграцию. НИКОГДА не использовать flywayClean на production!

### 14.6 Дерево решений для критических ситуаций

1. Приложение не отвечает:
   - Проверить логи: `flyctl logs`
   - Проверить health endpoint
   - Перезапустить: `flyctl restart`

2. Ошибка подключения к БД:
   - Проверить статус PostgreSQL
   - Проверить credentials
   - Проверить firewall rules

3. Утечка данных:
   - Немедленно отключить compromised аккаунт
   - Проанализировать логи аудита
   - Уведомить затронутых пользователей

| Refresh token race condition | Known (partial fix) | В http.ts есть refreshPromise-дедупликатор, предотвращающий параллельные refresh-запросы. Но при burst 401 ошибок возможны edge cases. |
| Caffeine cache без recordStats() | Known | WARN в логах, не влияет на работу |

### 15.2 Технический долг

**CRM Access Service** — изоляция реализована программно, не на уровне СУБД (Row Level Security). Это работоспособно, но менее надёжно при сложных запросах.

**Task Pool Performance** — при большом количестве задач в пуле может потребоваться виртуализация или пагинация.

**Frontend Bundle Size** —，随着 развитии проекта bundle может расти. Рекомендуется code splitting и lazy loading для редко используемых фич.

### 15.3 Out of Scope (не в планах)

- Интеграция с 1С (Epic-13) — требует отдельного проекта
- Push-уведомления (мобильные) — только email и Telegram
- Мультитенантность — несколько компаний в одном инстансе
- GraphQL API — REST достаточно для текущих потребностей

### Б.1 Пример сервиса с проверкой доступа

```java
@Service
@RequiredArgsConstructor
@Slf4j
public class TaskService {
    
    private final TaskRepository taskRepository;
    private final CrmAccessService crmAccessService;
    private final TaskMapper taskMapper;
    private final NotificationService notificationService;
    
    public TaskDto createTask(TaskCreateRequest request, Long userId) {
        // Проверка доступа к клиенту
        if (request.getClientId() != null) {
            if (!crmAccessService.canAccessClient(userId, request.getClientId())) {
                throw new AccessDeniedException("Cannot create task for this client");
            }
        }
        
        Task task = taskMapper.toEntity(request);
        task.setCreatedByUserId(userId);
        task.setStageId(request.getStageId());
        task.setStatus(TaskStatus.OPEN);
        task.setCreatedAt(LocalDateTime.now());
        task.setUpdatedAt(LocalDateTime.now());
        
        Task saved = taskRepository.save(task);
        
        log.info("Task created: id={}, by user={}", saved.getId(), userId);
        
        return taskMapper.toDto(saved);
    }
    
    public TaskDto updateTask(Long taskId, TaskUpdateRequest request, Long userId) {
        Task task = taskRepository.findById(taskId)
            .orElseThrow(() -> new NotFoundException("Task not found: " + taskId));
        
        // Row-level access check
        if (!crmAccessService.canAccessTask(userId, task)) {
            throw new AccessDeniedException("Cannot modify this task");
        }
        
        // Business rule: can't modify completed tasks
        if (task.getStatus() == TaskStatus.DONE) {
            throw new BusinessException("Cannot modify completed task");
        }
        
        // Update fields
        if (request.getTitle() != null) {
            task.setTitle(request.getTitle());
        }
        if (request.getDescription() != null) {
            task.setDescription(request.getDescription());
        }
        if (request.getPriority() != null) {
            task.setPriority(request.getPriority());
        }
        if (request.getDueDate() != null) {
            task.setDueDate(request.getDueDate());
        }
        
        task.setUpdatedAt(LocalDateTime.now());
        Task saved = taskRepository.save(task);
        
        return taskMapper.toDto(saved);
    }
    
    public List<TaskDto> getTasksByStage(Long stageId, Long userId, String role) {
        // Different access rules for different roles
        if (role.equals("ADMIN") || role.equals("ADVISOR")) {
            // Full access
            return taskRepository.findByStageIdOrderByPosition(stageId)
                .stream()
                .map(taskMapper::toDto)
                .toList();
        } else {
            // Only assigned tasks
            return taskRepository.findByStageIdAndAssignedUserId(stageId, userId)
                .stream()
                .map(taskMapper::toDto)
                .toList();
        }
    }
    
    @Transactional
    public TaskDto assignTask(Long taskId, Long assigneeId, Long userId) {
        Task task = taskRepository.findById(taskId)
            .orElseThrow(() -> new NotFoundException("Task not found"));
        
        // Only admin/advisor can reassign
        String userRole = crmAccessService.getUserRole(userId);
        if (!userRole.equals("ADMIN") && !userRole.equals("ADVISOR")) {
            if (!task.getAssignedUserId().equals(userId)) {
                throw new AccessDeniedException("Can only reassign own tasks");
            }
        }
        
        // Task Pool reopening logic
        if (task.getStage() != null && 
            task.getStage().getType() == StageType.LOST) {
            Long firstOpenStageId = pipelineService.getFirstOpenStageId(
                task.getStage().getPipelineId()
            );
            task.setStageId(firstOpenStageId);
            log.info("Task {} reopened from LOST to first OPEN stage", taskId);
        }
        
        task.setAssignedUserId(assigneeId);
        task.setUpdatedAt(LocalDateTime.now());
        
        Task saved = taskRepository.save(task);
        
        // Notify assignee
        notificationService.notifyTaskAssigned(assigneeId, saved);
        
        return taskMapper.toDto(saved);
    }
}
```

```java
@RestController

public class TaskController {

            @RequestParam(required = false) Long stageId,

            @RequestParam(required = false) Long assignedUserId,
            @RequestParam(required = false) TaskStatus status,
            @RequestParam(defaultValue = "0") int page,
```

```typescript
// features/chat/hooks/useChat.ts
export function useChat() {
  const { user } = useAuth();
  const [messages, setMessages] = useState<ChatMessage[]>([]);
  const [contacts, setContacts] = useState<ChatContact[]>([]);
  const [activeContact, setActiveContact] = useState<ChatContact | null>(null);
  const [isConnected, setIsConnected] = useState(false);
  
  const stompClient = useRef<Stomp.Client | null>(null);
  
  // Load contacts on mount
  useEffect(() => {
    chatApi.getContacts().then((response) => {
      setContacts(response.data);
    });
  }, []);
  
  // Load messages when active contact changes
  useEffect(() => {
    if (!activeContact) return;
    
    chatApi.getMessages(activeContact.id).then((response) => {
      setMessages(response.data);
    });
  }, [activeContact]);
  
  // Connect to WebSocket
  useEffect(() => {
    if (!user) return;
    
    const socket = new SockJS(getWsEndpointUrl());
    stompClient.current = Stomp.over(socket);
    
    stompClient.current.connect(
      { Authorization: `Bearer ${getAccessToken()}` },
      () => {
        setIsConnected(true);
        
        // Subscribe to personal messages
        stompClient.current?.subscribe(
          `/topic/chat/${user.id}`,
          (message) => {
            const newMessage = JSON.parse(message.body) as ChatMessage;
            setMessages((prev) => [...prev, newMessage]);
          },
          { Authorization: `Bearer ${getAccessToken()}` }
        );
      },
      (error) => {
        console.error('WebSocket connection error:', error);
        setIsConnected(false);
      }
    );
    
    return () => {
      if (stompClient.current) {
        stompClient.current.disconnect();
      }
    };
  }, [user]);
  
  const sendMessage = (content: string) => {
    if (!stompClient.current || !activeContact) return;
    
    const message: SendMessageRequest = {
      recipientId: activeContact.id,
      content,
      messageType: 'TEXT',
    };
    
    stompClient.current.send(
      '/app/chat.send',
      { Authorization: `Bearer ${getAccessToken()}` },
      JSON.stringify(message)
    );
    
    // Optimistic update
    const optimisticMessage: ChatMessage = {
      id: Date.now(), // temporary ID
      senderId: user!.id,
      recipientId: activeContact.id,
      content,
      messageType: 'TEXT',
      createdAt: new Date().toISOString(),
    };
    
    setMessages((prev) => [...prev, optimisticMessage]);
  };
  
  return {
    messages,
    contacts,
    activeContact,
    setActiveContact,
    sendMessage,
    isConnected,
  };
}
```

**API (Application Programming Interface)** — набор правил и протоколов для взаимодействия между программами.
